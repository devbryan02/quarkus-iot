# Plan de creación del esqueleto de Kivo

Alcance autorizado: generar backend y frontend dentro de `codebase/`, con Java 25 LTS, Quarkus LTS, `npx create-next-app@latest`, Dockerfiles y Compose. No implementar funcionalidades del MVP ni generar todavía la app Flutter.

Se aplica la habilidad de planificación para registrar pasos y validación. Ejecución directa en `develop`, rama indicada por el propietario. La [spec funcional](../../../docs/superpowers/specs/2026-11-08-kivo-mvp-design.md) se conserva; la instrucción posterior del propietario sustituye Java 21 por Java 25 LTS.

## Estructura y decisiones

- `backend/`: generador Maven oficial de Quarkus 3.40.1.1 LTS, Java 25, REST Jackson y health; conservar ejemplo y pruebas generados como comprobación técnica, sin dominios de negocio.
- `frontend/`: create-next-app latest, TypeScript, App Router, ESLint, npm y `src/`; plantilla mínima sin pantallas funcionales.
- Dockerfiles multietapa: Java 25 para compilación y ejecución; Node 24 LTS y salida standalone para Next.js; usuarios sin privilegios.
- `compose.yaml`: backend y frontend accesibles solo en localhost; perfil `infra` para PostgreSQL, Redis y Kafka, sin persistencia de negocio ni integraciones ficticias.
- Actualizar npm si hay parche disponible y revisar `npm audit`, aplicando correcciones compatibles. No usar `audit fix --force` ni introducir cambios mayores sin revisar.

## Criterios de entrega

Los dos esqueletos compilan, incluyen comandos reproducibles y sus contextos Docker no copian secretos, cachés o dependencias locales. Compose configura redes y healthchecks sin exigir servicios externos para arrancar los esqueletos. Una revisión independiente final comprueba configuración y reproducibilidad. Los resultados de auditoría describen únicamente el alcance realmente analizado.

## Resultados y decisiones de ejecución

- Maven Wrapper `verify -DskipITs=false`: BUILD SUCCESS, prueba Quarkus y prueba de integración del JAR, ambas con 0 fallos/errores. El generador se conserva sin lógica del producto.
- Frontend: `npm ci`, lint, TypeScript y build de producción correctos. Auditoría completa y `--omit=dev`: **0 vulnerabilidades reportadas** al ejecutar esta entrega.
- El árbol inicial reportó 8 vulnerabilidades moderadas. Probar ESLint 10 no corrigió el problema y produjo advertencias de compatibilidad; se conservó ESLint 9 del generador y se fijó únicamente `minimatch@>=7.0.0 <11.0.1` a 11.0.5. La instalación limpia y validaciones comprobaron el resultado. Revisar ese override cuando los paquetes superiores incorporen el arreglo.
- Dockerfiles construidos desde fuente. Backend requiere `unzip` en build: sin él, el wrapper elige TAR.GZ pero conserva el checksum ZIP; se corrigió instalando `unzip`, sin eliminar la validación.
- `docker compose config --quiet` con y sin perfil `infra`: correcto. Los cinco servicios arrancaron saludables. HTTP `/hello` devolvió el texto del generador, `/q/health/ready` indicó UP y el frontend devolvió HTTP 200 con Kivo. Runtime Docker observado: Java 25.0.5 LTS y Node 24.22.2.
- Se detuvieron los contenedores de prueba mediante `docker compose --profile infra down`; no se borraron volúmenes. La contraseña aleatoria de prueba está solo en `codebase/.env`, ignorado por Git.
- Revisión independiente: se corrigió dependencia de `LayoutProps` generado usando un tipo explícito de `children`. La comprobación aislada sin `.next/types` falló antes y pasó después. Se tradujeron los README y se prepara el modo ejecutable de `mvnw` para clones Linux.
- Enlaces de documentación resueltos y archivos generados excluidos de Git. No se auditó Java o CVEs de imágenes ni se validaron funciones del MVP; `npm audit` solo acredita el árbol npm en ese momento.

Publicación: el historial y el estado remoto de `develop` son la evidencia del commit/push; no se integra a `main` en esta entrega.
